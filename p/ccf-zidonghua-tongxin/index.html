自动化、通信协议、串口——我搞懂的那些事

现场设备和芯片里都在讲协议，我一开始全混了。这篇是理顺之后的笔记。

May 22, 2026

我为什么整理自动化与通信笔记

学电气自动化不可能绕开通信。我原来把「自动化」「协议」「串口」当成三个孤立名词——PLC 课讲 Modbus，单片机课讲 UART，现场又听 RS485，全混在一锅。后来才串起来：自动化管闭环控制，协议管比特怎么变成有意义的数据，串口管电线上怎么一位一位传。

这篇按我理解的推导顺序写，工业现场（PLC、Modbus）和芯片侧（UART、SPI、I2C）用同一套逻辑对照。和 博图 TIA 笔记、虚拟调试 里的联调也能连上。

我理解的「基础」是什么意思

什么叫基础？

基础 = 回到 最不可再拆的核心问题，去掉类比、口号和习惯说法，只问：

  1. 世界/产线里到底存在什么？（物理事实）
  2. 要达成某个目标，缺什么、卡在哪？（根本矛盾）
  3. 最小必要手段是什么？（由此 推导出 概念，而不是先背定义）

这篇笔记 禁止 这种学法：「自动化就是 PLC + 机器人，串口就是 RS485，协议就是 Modbus」—— 那是 结论表，不是 推导链。

我总结的（先预告，后文逐条证明）：

概念从什么核心问题推导出来最小定义
自动化人的操作 慢、不准、不可 7×24；期望输出必须 可重复用 可执行的确定逻辑 驱动 感知—决策—执行—反馈 闭环
通信协议电信号只有高低/脉冲，本身不含「温度 25℃」的含义收发双方对 比特如何组织成有意义报文 的 共同约定
通信串口多根线并行传 bit 贵且难布线；远距离要 抗干扰在 少数导线 上 按时间顺序逐位 传 0/1 的 硬件接口方式

自动化 —— 从「人为什么要控制机器」出发

更底层：产线里只有三样东西在流动

不管做手机还是做汽车，车间里 根本 只有三类东西：

流动什么例子谁关心
物质钢板、螺栓、半成品物流、工艺
能量电、气、液压设备、安全
信息温度多少、该停还是该走、故障码控制与自动化

自动化关心的根本对象不是「机器人好不好看」，而是：

如何让 信息 正确、及时地驱动 能量 与 物质 按期望运动。

人也可以传递信息（看表、拧阀门、按按钮），但人会 疲劳、走神、反应慢、记错步骤。
根本矛盾： 期望产出 稳定、快速、可重复 ↔ 人工操作 不确定。

从「手拧阀门」到「可编程逻辑」

阶段信息存在哪根本局限
纯人工老师傅脑子里不可复制、不可 7×24、难审计
硬接线继电器物理接线图改逻辑要改线，柔性差
PLC / 工控机程序（软逻辑）改程序即可换工艺，可重复扫描执行
+ 通信程序可读 远程设备 的数据单台 PLC 的 I/O 点有限，设备分散

推导 2： 「自动化」不是买一个机器人，而是 把操作步骤从人脑/硬接线，迁移成可重复执行的逻辑，并接入测量与执行机构。

推导 3： 当传感器、变频器、仪表不在 PLC 本体 I/O 板上时，必须跨空间传信息 → 自然引出第二、三章（协议与串口）。

自动化的根本定义（由 1.1～1.3 推出）

自动化 = 在少人干预下，由 控制器 按 确定周期或事件 执行 预定逻辑，通过 感知与执行机构 使系统输出 接近期望，并 可测量、可重复、可诊断。

关键词都来自推导，不是口号：

  • 确定周期：PLC 常见几 ms～几十 ms 扫一圈；确定性是工业安全的基础。
  • 可诊断：出了错要能查是传感器假、通信断，还是程序 bug —— 否则无法维护。

解构：感知 — 决策 — 执行 — 反馈

我总结的： 自动化 = 闭环控制 + 可编程逻辑 +（通常）跨设备信息交换。

为什么工业要分「现场 / 控制 / 监控 / 管理」层？

这不是 marketing 分层，而是 责任与实时性 推导出来的：

层级根本要解决的问题时间尺度
现场设备物理世界 true/false、电流电压毫秒级
控制层（PLC）安全联锁、顺序、节拍毫秒～百毫秒
监控层（HMI/SCADA）人看、人改参数、报警百毫秒～秒
管理层（MES/ERP）排产、成本、追溯分钟～天

推导 4： 把 MES 的慢逻辑和 PLC 的急停缠在一起，违反 时间尺度分离 —— 所以分层是 工程必然，不是文档好看。

通信协议 —— 从「信息如何跨空间传递」出发

更底层：信息必须物化为物理信号

控制器和远处的变频器之间没有「心灵感应」。
物理事实： 跨空间只能传 物质携带的能量/信号 —— 最常见是 导线上的电压、电流，或 光纤里的光，或 电磁波。

层级是什么根本
物理层电压高低、光有无能传 0 和 1 的载体
还不构成「温度 25℃」—0/1 本身 无业务含义

核心问题： 如何把 一串 0/1 变成 「站号 3 的温度是 25.0℃」？
答案只能是： 双方事先 约定规则 —— 这就是 协议 存在的根本原因。

信号 ≠ 语义：为什么「接上線」不够

假设 A 设备发：01 03 00 00 00 01 84 0A（8 个字节）

若 B 的理解B 的行为
懂 Modbus RTU解析为：读 3 号站、功能码 03、起始地址 0、长度 1…
不懂，按 ASCII 文本乱码
懂 Modbus 但字节序相反CRC 错、拒收
波特率与 A 不一致采样时刻错，整帧废掉

推导 5： 通信失败只有四类 根本原因：

  1. 物理不通（线断、接反、干扰）
  2. 物理层参数不一致（波特率、电平标准）
  3. 链路层帧格式不一致（从哪开始一帧、校验方式）
  4. 应用层语义不一致（同一地址表示不同含义）

协议 主要解决 3 和 4；串口/RS485 主要解决 1 和 2 中的一部分。

通信协议的根本定义

通信协议 = 发送方与接收方关于 比特流如何分帧、如何寻址、如何编码数值、如何检错与响应 的 公开或厂商约定的规则集合。

类比（仅辅助，不替代推导）：

  • 物理通道 = 电话线是否通
  • 协议 = 双方是否都说 同一套语法
  • 报文 = 一句完整的话

我总结的： 协议是 信息的「语法+词典」；没有它，比特流只是 噪声。

极简推导实例：Modbus 读寄存器在解决什么

业务问题（应用层）： PLC 需要知道 温度表内部变量「当前温度」的数值。

协议做的事：

  1. 规定 请求帧 各字节含义（站号、功能码 03=读保持寄存器、地址、长度、CRC）
  2. 规定 从站必须应答，否则主站超时判失败
  3. 规定 寄存器地址与数据类型 的映射（如地址 0 = 温度 ×10 的整数）

根本要点： Modbus 不关心 RS485 还是 TCP —— 同一 应用层语义 可跑在不同 物理通道 上；这再次说明 协议 ≠ 串口。

通信协议的工作原理是什么？（根本全流程）

上一节知道协议 是什么；本节从核心问题推导协议 怎么工作 —— 任意工业协议，再复杂，都逃不出下面这条链。

.1 核心问题：A 如何让 B「知道一件事并（可选）做事」？

步骤根本在问什么
1A 要把 意图（读温度 / 写转速 / 急停）变成 比特
2B 要从 线上比特 还原 意图
3双方要确认 有没有传对、传完、谁说的
4出错时 怎么发现、怎么重试、何时放弃

协议的工作原理 = 对上述四问给出 确定性答案 的一整套机制。

步骤名称根本在做什么失败会怎样

② 组帧加「信封」站号、功能码、长度、CRC 等收端不知道帧从哪到哪
③ 发送物化到介质按波特率/以太网帧发到 RS485/网线物理层不通
④ 同步认帧找帧边界起始位、空闲间隔、以太网前导码整帧错位
⑤ 检错/超时可信性CRC 比对；主站等应答超时静默失败或误动作
⑥ 解析比特 → 结构按协议拆字段、查功能码表拒收或误解
⑦ 应用驱动行为更新内存映射、写 I/O、报警业务层无响应

推导 9： 我调通信故障时，永远在这七步里定位 —— 不是「玄学」。

.3 三种交互模型（决定协议「怎么跑」）

协议不只定义 帧长什么样，还定义 谁先说、何时说 —— 这是 工作原理 的核心分支：

模型根本工作方式典型协议
主从问答（Request-Response）一方 提问，另一方 必须回答主站发请求 → 从站应答 → 主站超时判失败Modbus RTU/TCP
循环过程数据（Cyclic I/O）控制周期内 反复交换固定 IO 映像每 1～10 ms 自动刷新输入输出表，无需每次「读寄存器」Profinet IO、EtherCAT PDO
发布/订阅（Publish-Subscribe）生产者 广播，订阅者 自取主题/节点上挂数据，谁关心谁订阅MQTT、部分 OPC UA 用法

主从问答：  主 ──问──→ 从 ──答──→ 主     （像打电话，一问一答）
循环 IO：   主 ←──────→ 从 ←──────→ 主   （像每拍「同步快照」，双方表格自动刷新）
发布订阅：  源 ──发布──→ 总线 ←──订阅── 多个客户端   （像公众号推送）

我总结的：

  • 读 occasional 仪表 → 主从 够用；
  • 伺服、分布式 IO 要 确定性周期 → 循环 IO；
  • 跨系统、跨车间上报 → 发布订阅 / 信息模型。

.4 以 Modbus RTU「读保持寄存器」走一遍七步链

场景： PLC（主站，站号可任意）读 3 号从站（温度表）地址 0 的 1 个寄存器。

步骤实际发生的事
① 编码业务意图 =「读地址 0、长度 1」→ 功能码 03，起始地址 0x0000，数量 0x0001
② 组帧01 03 00 00 00 01 + CRC16 84 0A（整帧 8 字节；01 为从站地址）
③ 发送UART 按 9600-8-N-1 逐 bit 推到 RS485 A/B 线；总线上 同一时刻只允许一帧（半双工）
④ 认帧从站 UART 见起始位 → 收满 8 字节 → 按 Modbus 规则判帧结束（RTU 用 3.5 字符间隔）
⑤ 检错从站重算 CRC，不对则 丢弃、不应答；主站等应答超时 → 报通信故障
⑥ 解析从站：功能码 03 → 读内部寄存器 0 → 得到值 250（表示 25.0℃）
⑦ 应用从站组应答帧 01 03 02 00 FA ...；主站收到后写入 PLC 内存字，程序里 250/10 显示

推导 10： Modbus 的「简单」= 只有 主从问答 + 寄存器映射，没有复杂的设备对象模型 —— 代价是 大数据量、高实时多轴 时不占优。

.5 以 Profinet IO 循环模型对比（同一条链，不同机制）

对比项Modbus RTUProfinet IO
交互每次读都要 发一问一答组态后 每周期自动交换 IO 表
实时性取决于轮询多少从站交换周期 组态可设（如 1 ms 级）
语义寄存器地址 + 功能码设备描述文件（GSD）+ 槽位/子模块
工作原理重心解析请求帧周期性过程数据 + 报警/参数通道

我总结的： 不是 Profinet「更高级所以更好」，而是 问题从「偶尔读几个数」变成「每毫秒同步上百 IO 点」 → 交互模型必须换。

.6 超时、重试与仲裁（工作原理里的「时间规则」）

机制根本解决什么
超时应答没回来 → 不能无限等，否则 PLC 扫描卡死
重试偶发干扰 → 再发 1～3 次；工业上 重试次数必须有限
总线仲裁多主或冲突 → 谁有权占用介质（以太网 CSMA/CD、CAN 按 ID 优先级）
半双工互斥RS485 上主站发完才能收 → 协议规定 帧间隔 避免碰撞

通信协议工作原理的完整定义（由 2.6.1～2.6.6 推出）：

在约定物理通道上，按 既定交互模型，完成 编码→组帧→传输→认帧→检错→解析→应用 的闭环；并在 时间维度 上规定超时、周期与仲裁，使 语义 可靠地跨越空间。

通信串口 —— 从「如何用导线传 0 和 1」出发

更底层：为什么用二进制

数字电路 根本 只有两种稳定状态：高电平 / 低电平（或光的有无）。
一个瞬间用一个电压表示 1 bit 信息。
8 bit = 1 byte，可编码 0～255 或一个 ASCII 字符 —— 编码方式 又是上一层约定。

并行 vs 串行：物理约束下的必然权衡

方式根本做法优点缺点
并行多根线 同时 传多个 bit同一时刻吞吐大线多、贵、长线 ** skew（时差）** 严重
串行一根（或一对）线按时间 一位位传线少、适合远距离、芯片引脚省同样带宽下 时间更长

推导 7： 工业现场设备分散、距离米～百米 → 串行 是 成本与可靠性 推导出的主流之一（另一主流是以太网，用更高时钟换距离与规模）。

串口（Serial Port）的根本定义：

串口 = 采用 串行方式 在 异步或同步时序 下，在 有限数量的物理引脚/线对 上传输 二进制比特流 的 接口形态。

异步串行：时间维度上的根本约定

两根设备用 UART 异步 通信时，没有单独的「时钟线」，只能靠 双方约定同一比特时间。

一帧典型结构（推导「为什么要起始位、停止位」）：

空闲 ──→ [起始位0] [数据位 d0～d7] [可选校验] [停止位1] ──→ 空闲

    告诉接收方「开始了」            告诉接收方「这一帧结束」
参数含义不一致的后果
波特率每个 bit 占多长 时间采样点错，全帧乱

例：9600-8-N-1 = 每秒 9600 bit、8 数据位、无校验、1 停止位 —— 这是 物理层时序协议，还 不是 Modbus。

从 UART 到 RS-232 / RS-485：芯片语言 vs 现场语言

推导 8： 芯片引脚输出的是 TTL 电平（如 0V/3.3V）， 不能直接 长距离拉到 noisy 车间 —— 需要 电气标准 规定 电压范围、阻抗、共地、抗干扰。

名称根本是什么推导出的用途
UART / TTL芯片 直接 的异步串行逻辑板内、模块、USB 转串口小板
RS-232点对点、电平转换、距离 短老设备、调试口
RS-485差分（A-B 电压差），半双工总线一台 PLC 对 多台 从站，抗干扰
USB 虚拟 COMPC 用 USB 模拟串口设备笔记本无物理 COM 口时代

口语「串口通信」在 Windows 常指 COM 口；在 PLC 柜常指 RS485 物理层 + UART 帧时序 + Modbus RTU 应用层 —— 三层叠在一起，初学者必须 拆开看。

RS-485 为何在工业现场占主流？（从问题推导，不是背优点）

问题 A： 十台仪表，若每台点对点 RS-232 → 线缆数量暴增、PLC 端口不够。
推导： 需要 总线 —— 多设备 共享一对线，用 站号 区分（协议层解决寻址）。

问题 B： 电机、变频器干扰大，单端信号易误判。
推导： 需要 差分信号（RS-485）—— 看 A-B 差值，共模干扰被抵消。

串口 vs 以太网：同一推导框架下的两种解

根本需求串行现场总线（RS485 等）以太网
低成本接大量廉价仪表优往往 overkill
高带宽、多节点、拓扑灵活弱优
百米内 kbps～Mbps 够够更够

我总结的： 不是「串口过时」，而是 问题规模不同 → 物理层选型不同；现代产线 两者并存 是常态。

串口与协议的分界（全文最易混点）

层次例子根本职责
串口 / RS485波特率 9600、A/B 线比特怎么在时间上、导线上出现
Modbus RTU功能码、寄存器、CRC**这些比特 代表什么指令

接上 RS485 线 ≠ 能通信 —— 还必须 波特率一致 + 协议一致 + 站号正确 + 极性/终端电阻正确。

一一对比（1）：Modbus RTU vs Modbus TCP

共同根本： 同一 应用层语义（功能码、寄存器概念）。

维度Modbus RTUModbus TCP
物理层RS485 串口以太网（RJ45）
帧封装站号 + PDU + CRC16MBAP 头 + PDU（无 CRC，靠 TCP）
寻址串口 从站号 1～247IP 地址 + 端口 502
交互主从、半双工总线主从、TCP 连接可多客户端
速度/距离通常 9600～115200 bps，百米级Mbps 级，跨交换机/车间
典型用途变频器、仪表现场串接上位机、SCADA、PLC 网口读数据
根本选型设备只有 RS485、成本低已有以太网、要远程/多主站读

区别一句话： 语义相同，信封与邮路不同 —— RTU 走串口 CRC 帧，TCP 走 IP 套接字。

一一对比（2）：Modbus vs Profinet

维度Modbus（RTU/TCP）Profinet
出身开放、跨厂商 de facto 标准西门子主导、IEC 61158 现场总线族
数据模型** flat 寄存器表**（地址+功能码）GSD 设备模型（槽位/模块/IO 映像）
交互模型主从问答（读/写才交换）Profinet IO： cyclic 过程数据 + 非实时参数通道
实时性取决于轮询周期，抖动较大可组 1～10 ms 级 确定性交换（IRT 更严）
组态手动填站号、地址表TIA Portal 拖硬件、自动分配 IO 地址
生态几乎任何仪表都支持西门子 PLC、驱动、IO 最优
根本选型第三方杂牌设备、简单读写西门子产线、分布式 IO、驱动一体化

区别一句话： Modbus = 「寄存器电话簿，要问才答」；Profinet IO = 「组态好后 IO 表每拍自动同步」。

一一对比（3）：Profinet vs Profibus

维度Profibus DPProfinet IO
时代/介质90 年代 专用双绞线 RS485 类以太网 为主
根本当时要用 数字通信替代硬接线 IO以太网普及后 同一网线传 IT + 实时 IO
拓扑总线 + 终端电阻星型/树型（交换机）
与西门子关系S7-300/400 时代标配S7-1200/1500、博途 主推
现状存量改造、老设备维护新建项目主流

区别一句话： 同一家族、两代物理层 —— Profibus 是「上一代现场总线」，Profinet 是「以太网时代的继任」。

一一对比（4）：Profinet vs EtherCAT

维度Profinet IOEtherCAT
主导生态西门子、欧洲通用制造倍福 Beckhoff 系、运动控制、半导体装备
以太网用法标准以太网帧 + 实时调度（IRT 走专用芯片）「飞读」：帧穿过节点，每站 硬件截取/插入 数据
实时机理周期 IO 交换 + 优先级分布式时钟同步、极低 jitter，适合 多轴伺服
组态工具博途TwinCAT、各品牌主站
根本选型西门子整线、通用离散制造高速运动、多轴同步、极短周期

区别一句话： 都要实时，但 EtherCAT 根本优化 「多轴同步 + 纳秒级时钟」；Profinet 根本优化 「西门子全栈 + 通用 IO/驱动」。

一一对比（5）：EtherCAT vs EtherNet/IP

维度EtherCATEtherNet/IP
标准背景IEC 61158，倍福技术路线ODVA，罗克韦尔 Rockwell 生态
协议栈自定义高效 PDO 过以太网标准 TCP/UDP + CIP 对象模型
实时硬件从站芯片 on-the-fly，周期可达 100 μs 级实时 IO 靠 Scheduled / CIP Sync 等，普遍 ms 级
北美/欧洲欧洲装备、日系部分北美产线、AB PLC 标配
根本选型运动控制、对 jitter 极敏感AB/罗克韦尔系、与 FactoryTalk 等集成

区别一句话： 都跑在以太网电缆上，但 实时哲学不同 —— EtherCAT 偏 专用硬件流水线；EtherNet/IP 偏 CIP 对象 + 罗克韦尔体系。

一一对比（6）：CANopen vs Modbus RTU

维度CANopenModbus RTU
物理层CAN 总线（差分、ID 仲裁）RS485（主从、站号）
寻址11/29 bit CAN ID + 对象字典索引从站号 + 寄存器地址
冲突处理非破坏性 按 ID 优先级仲裁主站 轮询，从站不主动发
数据模型对象字典 OD（标准化对象 0x6040 等）厂商自定义寄存器表
典型场景伺服、编码器、医疗、车辆通用仪表、变频器
根本选型多节点、设备要 主动上报、伺服协议统一简单、便宜、文档多是寄存器表

区别一句话： Modbus = 主站点名；CANopen = 带优先级的广播总线 + 标准对象字典。

一一对比（7）：OPC UA vs 现场总线（Modbus / Profinet / EtherCAT）

维度现场总线 / 现场协议OPC UA
根本层级现场层、控制层 —— 让 PLC 驱动设备信息层 —— 让 不同系统理解同一数据含义
数据模型寄存器 / IO 映像 / PDO节点 + 引用 + 信息模型（可带语义、单位）

区别一句话： 现场总线回答 「怎么控」；OPC UA 回答 「数据叫什么、什么意思、谁能安全访问」 —— 互补，不替代。

一一对比（8）：OPC UA vs MQTT

维度OPC UAMQTT
根本工业互操作 + 强类型信息模型轻量消息到达（物联网/pub-sub）

典型场景MES 读 PLC、跨厂商 SCADA云平台、海量终端上报、远程监控
根本选型工厂内 结构化数据集成上云、弱网、多对多广播

区别一句话： OPC UA = 工业版「带字典的 API」；MQTT = 工业版「微信群发通知」。

集成电路层面的通信协议与串行接口 —— 从基础分析

与前面章节的关系： 第二～三章、2.6、第六章讲的是 产线设备之间（米～百米）；本章讲 同一块 PCB 上、芯片与芯片之间（毫米～几十厘米）。
根本不变： 仍是 信息物化为 0/1 → 串行/并行通道 → 协议赋予语义 → 七步链闭环；变的是 距离、速度、引脚成本、集成度。

更底层：一颗芯片内部、一块板子上到底在传什么？

尺度谁在和谁说话根本矛盾
芯片内部CPU 核 ↔ 外设控制器 ↔ 片上 RAM硅面积、时钟域、功耗
同一块 PCBMCU ↔ 温湿度传感器 ↔ Flash ↔ 显示屏引脚数有限、线要短、要便宜
设备内部模块工控板 MCU ↔ 隔离 RS485 芯片 ↔ 端子要把 芯片语言 变成 现场语言
产线PLC ↔ 变频器第三章、第六章

推导 13： 集成电路通信的根本矛盾 = 功能越来越多 ↔ 引脚就那么多、PCB 面积有限、功耗要低。

→ 和第三章一样，结论仍是：串行优于并行（除片内超宽总线外）；差别在于芯片上还要在 线数、速度、多设备、谁当主 之间做更精细的权衡。

.3 逐类根本说明（是什么、解决什么）

类别代表根本解决什么典型芯片/模块
A. 异步串行UART / USART只有数据线，靠波特率对齐；实现最简单STM32 USART、GPS 模块 NMEA
B. 同步主从（全双工）SPI / QSPI有 CLK，高速、点对点；片选 CS 区分多从机Flash W25Q、某些 ADC
C. 同步主从（半双工总线）I2C / SMBus / PMBus只用 2 线 挂多个设备，地址寻址温湿度 SHT、EEPROM 24Cxx、电源芯片
D. 单线总线1-Wire极致省 pin（数据+供电共线）DS18B20 温度
E. 多节点仲裁CAN / LIN多节点、抗干扰、按 ID 优先级车身网络、伺服驱动器内部
F. 主机标准接口USB / PCIe / SDIO连接 PC 或 高速大块数据U 盘、NVMe、SD 卡
G. 音频/显示I2S / MIPI流式采样或 屏幕像素流codec、摄像头、LCD
H. 片内 SoC 总线AXI / APB芯片 内部 IP 核互联ARM SoC 内部
I. 调试SWD / JTAG下载程序、断点调试ST-Link、J-Link
J. 电平/介质翻译RS232/485 收发器、PHYTTL ↔ 现场电平/以太网MAX485、LAN8720

通信协议在集成电路里怎么工作？（同一套七步链）

第二章 2.6 的七步链 完全适用；以 MCU 经 I2C 读温湿度传感器 为例：

步骤I2C 上发生的事
① 编码要读「湿度」→ 传感器手册规定寄存器地址 0x25
② 组帧START + 7bit 地址(写) + ACK + 寄存器指针 + REPEAT START + 地址(读) + 读 2 字节 + STOP
③ 发送SCL 时钟下，SDA 逐 bit 翻转（同步串行）
④ 认帧每个字节 9 时钟：8 数据 + 1 ACK；START/STOP 定界
⑤ 检错无 ACK → 设备不存在或忙；上层可超时重试
⑥ 解析两字节拼成 16 bit 湿度 raw 值
⑦ 应用按手册公式换算 %RH，写入 MCU 变量

以 SPI 读 Flash 芯片 ID 为例（同步、全双工）：

步骤SPI 上发生的事
① 编码发读 ID 命令 0x9F
② 组帧拉低 CS → CLK 下 MOSI 发命令 → MISO 同时 收 3 字节 ID
③ 发送主机驱动 CLK；无起始位，靠 CS 片选框定「会话」
④～⑦主机按 CLK 边沿采样 MISO → 得到 Manufacturer/Device ID

推导 14： 芯片协议 更贴近硬件 —— 很多没有 Modbus 那种「功能码表」，而是 「寄存器手册 = 应用层协议」。

一一对比（集成电路篇）

.1 UART vs SPI

维度UARTSPI
同步异步（无 CLK 线，靠波特率）同步（有 CLK）
线数2～3（TX/RX/GND，可选流控）4+（CLK/MOSI/MISO/CS）
双工全双工（TX/RX 各一根）全双工（同时 MOSI/MISO）
多从机难（需多 UART 或 RS485 总线）多个 CS 挂同一总线
速度通常 9600～3 Mbps常见 1～50 Mbps+
根本选型调试打印、GPS、Modbus 从 UART 出Flash、屏、高速 ADC

一句话： UART = 「对表说话，各喊各的波特率」；SPI = 「跟着时钟拍，主机拉 CS 点名」。

.2 SPI vs I2C

维度SPII2C
线数3+Ncs（CLK/MOSI/MISO + 片选）2 线（SDA/SCL）+ 上拉
寻址硬件 CS 引脚 选设备7/10 bit 地址 在帧里
速度通常 更快Fast mode 400 kHz，Hs 3.4 MHz
拓扑点对点为主，CS 树总线，多设备并联
冲突主机完全控制多主时需 仲裁
协议层无统一标准，看芯片手册有 I2C 规范；SMBus/PMBus 子集
根本选型要快、从机不多、有足够 pinpin 不够、多传感器挂一条总线

一句话： SPI 用 线换速度；I2C 用 地址换 pin 数。

.3 I2C vs SMBus vs PMBus

维度I2CSMBusPMBus
根本通用 两线串行总线PC 电源管理 子集，时序更严电源/电源模块 监控，基于 SMBus
超时较宽松必须超时 防总线锁死同 SMBus 思路
电压多种常 3.3 V同左
典型设备传感器、EEPROM电池 gauge、主板 PMICDC-DC、服务器 PSU

一句话： SMBus/PMBus = I2C 物理层 + 更严的「工业级规矩」+ 特定寄存器语义。

.4 I2C vs 1-Wire

维度I2C1-Wire
线数SDA + SCL1 根数据（常含寄生供电）
速度kHz～MHz通常 15～125 kbps
设备海量标准 ICDallas/Maxim 系传感器、iButton
根本通用、生态大极致省线、距离短、设备少

一句话： 1-Wire = 「一根线凑合用」；I2C = 「两线换可靠与生态」。

.5 UART vs USB

维度UARTUSB
根本简单 bit 流主机中心 的完整生态系统
线TX/RXD+/D- 差分 + 供电 + 协议栈
软件发字节即可描述符、端点、类驱动（CDC/HID/Mass Storage）
速度kbps～Mbps12 Mbps～10 Gbps+
PC 连接需 USB-UART 桥（CH340）原生
根本选型MCU 调试、Modbus、老模块U 盘、相机、Android ADB、高速传感

一句话： UART = 裸比特管道；USB = 带操作系统参与的标准化管道。

.6 CAN vs UART（及 RS485 工业链）

维度CAN（片上有 CAN 控制器）UART + MAX485
物理CAN_H/CAN_L 差分TTL UART → RS485 收发器
多节点原生总线，ID 仲裁RS485 半双工总线 + 主从协议
冲突非破坏性按 ID 优先级主站轮询，从站不抢
工业协议CANopen、J1939Modbus RTU
根本车内、伺服、要 主动广播仪表、变频器、简单主从

一句话： CAN = 芯片级「大家都能喊，按 ID 决定谁赢」；UART+485 = 「主站点名」，与第六章 Modbus 一脉相承。

.7 SPI vs QSPI

维度SPIQSPI
线1 MOSI + 1 MISO4 线 IO 并行传（或 DDR）
根本够用、便宜Flash 容量大、要更快读取
场景小 Flash、一般外设128 Mbit+ NOR Flash、XiP 执行

一句话： QSPI = SPI 的「四车道版」，为 大容量存储 而生。

.8 片内 AXI 总线 vs 片外 SPI/I2C

维度AXI / APB（片内）SPI / I2C（片外引脚）
根本CPU 核访问 片上 IPCPU 访问 板级外设芯片
距离微米～毫米（芯片内）厘米级 PCB
宽度可 32/64/128 bit 并行串行 1～4 线
协议ARM AMBA 规范各厂商手册
我能否用探头量一般 摸不到示波器探头能在引脚上量

一句话： AXI = 芯片内部的「高速公路」；SPI/I2C = 芯片对外的「出口」。

.9 I2S vs SPI（都是同步串行，易混）

维度I2SSPI
根本音频采样流（左/右声道、字长、LR 时钟）通用数据交换
信号BCLK、LRCLK、SDCLK、CS、MOSI、MISO
数据语义连续 PCM 样本命令+寄存器
交互模型流式 cyclic主从问答

一句话： I2S = 为声音定制的 SPI 类流；SPI = 通用。

常见误区（用根本纠正）

误区根本纠正
「自动化 = 机器人」机器人只是 执行器之一；大量产线是 PLC + 传送带 + 通信，无机械臂
「接上串口线就能通」物理通只是 推导链第一步；还缺 时序参数 + 协议 + 寻址
「串口 = Modbus」Modbus 是 应用层规则；可跑 RS485，也可跑 TCP
「协议越新越好」选型根本是 互通成本 + 现有设备能力 + 维护人员会什么
「学自动化先学机器人」根本应先 闭环 + 逻辑 + I/O + 一种现场通信，再扩展运动控制
「I2C 和 SPI 随便选一个」pin、速度、设备数量 推导不同：I2C 省线，SPI 要快
「UART 就是 USB」UART 是 裸异步串行；USB 是 完整主机协议栈 + 差分 + 供电
「芯片手册寄存器不算协议」寄存器地址+读写时序 = 应用层协议；只是没叫 Modbus 而已
「CAN 和 RS485 一样」CAN 是 ID 仲裁广播；485+Modbus 是 主站轮询（见 9.6.6）
